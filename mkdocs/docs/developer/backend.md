# Backend Architecture

**Stack:** Django 5.1 + Django REST Framework 3.15 + PostgreSQL 16, served via Daphne (ASGI).

The backend is a thin API layer for CivicTechJobs's owned domain: a CTJ-managed skill taxonomy, the volunteer qualifier flow (where users record skills with proficiency levels and supply availability), opportunity listings, and the matching algorithm that connects volunteers to opportunities. Reference data outside that scope — user identity, practice areas, roles, project metadata — is consumed from [PeopleDepot](https://github.com/hackforla/peopledepot), HfLA's central directory.

Django admin doubles as a project-manager-facing CMS for opportunity management *and* a management interface for the skill taxonomy; there is no separate admin UI.

## Data model

CTJ owns four concepts. Everything else is referenced by PeopleDepot UUID.

- **Skill** — CTJ-managed skill taxonomy. Fields: `name` (unique), `description`, and an array of practice-area PeopleDepot UUIDs (skills can be relevant across multiple CoPs). Curated through Django admin so the matching list can be tailored to CTJ's purposes rather than tracking PeopleDepot's broader skill data.
- **SkillMatrix** — JSON field mapping `{skill_uuid: mastery_level(1-5)}`. Skill UUIDs reference local `Skill` records; mastery levels are user-supplied. Shared between users (skills they have) and opportunities (skills they require) — it's the data structure the matching algorithm operates on.
- **Opportunity** — open volunteer position. Fields: project (PeopleDepot project UUID reference), role (PeopleDepot role UUID reference), `body` (description text), required skills (O2O to `SkillMatrix`), status enum (open / closed / on hold / filled / draft), `created_by` (FK to local `UserProfile`), and CTJ-specific fields (work environment, minimum experience, minimum hours).
- **UserProfile** — per-user CTJ-owned state. Fields: PeopleDepot user UUID (join key), community-of-practice reference (PeopleDepot CoP UUID, selected by the user during the qualifier flow), O2O to a SkillMatrix (`skills_learned_matrix`), availability (`max_available_hours`, `meeting_availability`), `is_project_manager` flag.

Reference data — user identity, practice-area taxonomy, role taxonomy, project metadata — is **not stored locally**. CTJ looks it up from PeopleDepot at request time using its UUID.

## API endpoints

Endpoints are scoped to CTJ's owned domain. Reference data is consumed directly from PeopleDepot and is not proxied through CTJ.

| Endpoint | Methods | Auth | Notes |
|----------|---------|------|-------|
| `/api/healthcheck` | GET | None | Uptime + version |
| `/api/skills/` | GET | None | CTJ skill taxonomy (consumed by the qualifier flow) |
| `/api/opportunities/` | GET, POST | POST: PMs | List / create |
| `/api/opportunities/{id}/` | GET, PUT, DELETE | PUT: creator, DELETE: any PM | Detail / update / delete |
| `/api/users/{pd_user_uuid}/` | GET, PUT | Authenticated, self only | UserProfile (CoP, skill matrix, availability) |

The matching endpoint (ranking opportunities against a user's SkillMatrix or vice versa) is part of the stage-2 backend rewrite — see "What's not built yet."

The OpenAPI spec is at [backend/openapi-schema.yml](backend/openapi-schema.yml) and is regenerated whenever `startServer.sh` runs.

Non-existent `/api/*` routes return a structured JSON 404.

## Auth

Authentication is delegated to AWS Cognito — the same user pool that backs PeopleDepot. The Django backend does not own login, signup, or token endpoints.

Flow:

1. User signs into Cognito via the Next.js frontend.
2. Next.js receives a JWT and validates it in middleware.
3. For protected mutations, Next.js server actions forward the validated JWT to this API in the `Authorization: Bearer <token>` header.
4. A custom DRF authentication backend in [backend/ctj_api/auth.py](backend/ctj_api/auth.py) verifies the token signature against Cognito's public keys and extracts the `sub` claim — the canonical user identifier shared between CTJ and PeopleDepot.

## Permissions

Custom DRF permission classes in [backend/ctj_api/permissions.py](backend/ctj_api/permissions.py):

- **OpportunityPermission** — anyone authenticated can read; only PMs can create; only the creator can update; any PM can delete.
- **UserProfilePermission** — users can only read or write their own SkillMatrix, CoP selection, and availability. (Renamed from `UserDetailPermission` to match the model rename.)

Skill taxonomy mutation is gated by Django admin's built-in staff permission, not a separate DRF class — the API only exposes `GET /api/skills/`.

PM status comes from the `is_project_manager` flag on the local `UserProfile` (renamed from `isProjectManager` to match Python conventions). It is set by an existing admin through Django admin.

## Django admin as CMS

Django admin at `/admin/` is the management interface for two CTJ-owned domains:

- **Opportunities** — PMs create and update opportunities directly.
- **Skill taxonomy** — admins curate the list of skills (add, edit, remove), set descriptions, and associate skills with PeopleDepot practice-area UUIDs.

Admins sign in with Cognito (admin auth uses the same custom JWT backend, gated to users with the staff flag).

Reference data outside CTJ's scope — practice areas, roles, projects, user identity — is **not** manageable through CTJ's admin. Those are owned by PeopleDepot and managed there.

## Frontend integration

The Next.js frontend talks to two APIs:

- **This Django API** for CTJ-owned data: skill taxonomy, opportunities, skill matrices, matching results, user profiles.
- **PeopleDepot API** for reference data: practice areas, roles, projects, user identity (name, email).

Server components and server actions in Next.js aggregate both sources in a single render pass. The browser never talks to either backend directly — Next.js owns the request boundary.

The qualifier flow exemplifies the split: the user's CoP selection draws from PeopleDepot's practice-areas endpoint, the skills they rate come from CTJ's `/api/skills/` endpoint, and the resulting SkillMatrix is saved to the user's CTJ `UserProfile`.

There is no `frontend_dist/` build copy; the Next.js container is deployed alongside Django, both behind a shared ingress.

## PeopleDepot integration

CTJ depends on PeopleDepot for reference data outside its skill-matching domain:

- **User identity** — Cognito subjects map 1:1 to PeopleDepot user records (name, email, basic profile).
- **Practice areas (Communities of Practice)** — taxonomy and descriptions.
- **Role / job-title taxonomy.**
- **Project metadata** — project name, meeting times, status, etc.

CTJ stores PeopleDepot UUIDs as references (e.g., `Opportunity.project_id` is a PeopleDepot project UUID, not a Django foreign key). The PeopleDepot client at [backend/ctj_api/clients/peopledepot.py](backend/ctj_api/clients/peopledepot.py) wraps the relevant PeopleDepot endpoints with typed Python interfaces.

## What's not built yet

These gaps are part of the stage-2 backend rewrite:

- **Cognito JWT authentication backend** — `auth.py` needs to be implemented.
- **PeopleDepot client** — `clients/peopledepot.py` needs to be implemented.
- **Data model migration:**
    - `CommunityOfPractice`, `Role`, `Project`, `CustomUser` models removed (data sourced from PeopleDepot)
    - `Skill` retained: gains a `description` field; M2M to local `CommunityOfPractice` replaced with an array of PeopleDepot CoP UUIDs
    - `UserProfile` introduced as a thin per-user anchor, replacing `CustomUser`; `isProjectManager` renamed to `is_project_manager`
    - `Opportunity` retained: `project` and `role` FKs become PeopleDepot UUID references; `created_by` FK now points to `UserProfile`
    - `SkillMatrix` retained as-is
- **User profile update endpoint** — `/api/users/{pd_user_uuid}/` currently supports `GET` only (existing `UserDetail` is `RetrieveAPIView`); `PUT` support is needed so the qualifier flow can write the user's CoP selection, skill matrix, and availability.
- **Matching algorithm** — backend logic and endpoint shape for ranking opportunities by SkillMatrix similarity.
- **Opportunity filtering / search** — list endpoint currently returns all opportunities with no query params.
